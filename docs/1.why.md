# 1. WHY - 왜 테스트를 작성해야 하는가?

## 1.1 변경할 때 지켜야 할 동작을 기록하기

주문 수량을 바꾸는 코드를 수정한다고 가정합니다. 주문 수량과 총액이 올바르게 바뀌고, 재고도 수량 차이만큼 조정되어야 합니다. 요청이 거절되면 세 값이 모두 유지되어야 합니다. 이 기대를 테스트로 남겨 두면 구현을 바꾼 뒤에도 같은 조건을 자동으로 확인할 수 있습니다. [주문 수량 스펙](5.spec-driven-development.md#51-주문-수량-스펙)

회귀 테스트는 한 번 해결한 문제가 다시 생겼을 때 어떤 동작이 깨졌는지 알려 줍니다. 테스트를 작성하면서 객체를 준비하기 어렵거나 많은 의존성을 대신해야 한다면, 한 클래스가 여러 책임을 맡고 있는지도 살펴볼 수 있습니다.

## 1.2 좋은 테스트의 FIRST 원칙

| 원칙 | 작성할 때 확인할 점 |
| --- | --- |
| Fast | 개발 중 자주 실행하는 테스트는 검증에 필요한 범위만 로드합니다. |
| Isolated | 다른 테스트의 실행 순서나 남긴 데이터를 가정하지 않습니다. |
| Repeatable | 입력 데이터와 환경이 같으면 여러 번 실행해도 같은 결과가 나옵니다. |
| Self-Validating | 어서션이 기대 결과를 판정합니다. 로그를 눈으로 확인하는 과정 없이 실패 원인을 좁힐 수 있습니다. |
| Timely | 새 동작을 구현하거나 버그를 고치는 시점에 그 동작을 검증할 테스트를 함께 작성합니다. |
